# Node.Js_Express.js-Learning

## API documentation

The interactive Swagger UI is available at `/api-docs` and the generated OpenAPI JSON at `/api-docs.json`. The spec is generated from the route annotations and documents authentication, bank accounts and transfers, Paypack deposits and webhooks, loan applications and repayments, and payroll operations.

## Bank administrators and members

Public self-signup is disabled. The System Admin creates each Bank Admin and assigns the employee to a bank, without a sub-branch assignment. The Bank Admin has bank-wide scope: they create Sub-branch Managers and other employees, assign each to a sub-branch, register members in a selected sub-branch, manage bank-wide member and employee access, and view accounts and loan applications across all of their bank's sub-branches. Sub-branch Managers are created by the Bank Admin and remain limited to their assigned branch. Finance Managers have view-only access to the bank-wide employee and customer-member directory. Data queries and status changes are scoped to the authenticated employee's bank; the client cannot choose another bank. OTP email verification remains enabled for accounts that have not been approved by their Bank Admin.

Existing employee accounts created under the earlier combined “Branch Manager / Bank Admin” role should be reviewed by the System Admin and assigned the `bank_admin` role if they are intended to administer the whole bank. Other employee roles must have a sub-branch assignment.

Every bank has a unique 12-digit bank account number. Each sub-branch is assigned a unique branch code derived from the bank number; both identifiers are shown in bank and branch selection controls.

Deploy the backend whenever these API routes change. The deployed API's `/api-docs.json` should include `/api/users/bank-admins`, `/api/users/members`, and the member `activate` and `deactivate` endpoints; otherwise the running backend is behind the frontend. The frontend's `VITE_API_URL` must point to the deployed backend.

## Personal account applications

Customers and employees can request a personal account from their dashboard by selecting a bank and sub-branch and uploading a National ID or passport as a JPEG, PNG, or PDF (maximum 1.4 MiB). The API checks the declared MIME type against the file signature, stores the document as an authenticated Cloudinary raw asset, and creates the account with pending status. Set `CLOUDINARY_URL` in the backend deployment secret manager; account requests fail explicitly if private Cloudinary storage is not configured.

Only the System Admin or the Accounts Manager assigned to the account's bank and sub-branch can retrieve the document through the authenticated API; the Cloudinary asset itself is not public and document contents are excluded from account-list responses. A reviewer must retrieve/view the ID before the pending account can be approved. The applicant can use the account for deposits, transfers, or loan eligibility only after approval activates it. Handle ID/passport retention and deletion according to the institution's approved privacy policy.

## Loan finance

Customers and employees may apply for a personal loan in their own name, using their own verified account and an active bank account at the selected branch. Customers are limited to their registered bank and require approved membership. Employees are limited to their assigned bank and branch; Bank Admins may select any branch in their assigned bank. Applicants can have only one application and cannot apply while they have an outstanding loan at another bank. The system sets the annual interest rate for every approved loan using `SYSTEM_ANNUAL_INTEREST_RATE` (12% by default). Managers approve or decline applications but cannot change the rate. The quoted installment and expected interest use reducing-balance amortization.

Bank account numbers are generated by the server as unique 12-digit numeric identifiers when a bank is created.

Before a transfer is submitted, search for a recipient by name and select one of their active accounts. Account numbers are masked to their first and last three digits in search results.

To preview repairs for banks with missing account numbers (and refresh their branch codes), run `npm run banks:backfill-identifiers`. Review the output, then run `npm run banks:backfill-identifiers -- --apply` to persist it. The script also repairs missing branch codes on other banks and preserves valid identifiers by default.

Branch address options are fetched from the CORS-enabled Rwanda Administrative Divisions API at `https://rda-api.kibongo.com`, cascading from province through village.

Repayments are recorded in whole RWF amounts. Accrued interest is calculated daily on the outstanding principal using a 365.25-day year, allocated before principal, and unpaid interest carries forward. Interest income counts only interest collected. Marking an approved loan as defaulted records its remaining principal as a loss. Reported net profit is collected interest income minus principal losses; it excludes operating expenses, funding costs, and tax.

Customers can test loan repayments using the isolated Python FastAPI service in `payment-service/`. Start it with `uvicorn main:app --app-dir payment-service --host 127.0.0.1 --port 8000` after installing `payment-service/requirements.txt`, and set the same high-entropy `PAYMENT_SIMULATOR_API_KEY` on the Python service and Node backend. The backend's `PAYMENT_SIMULATOR_URL` defaults to `http://127.0.0.1:8000`. Virtual channels include MTN Mobile Money, Airtel Money, bank transfer, and virtual account. The customer may explicitly simulate a decline for testing.

**The virtual simulator is not a payment provider.** A simulated success updates only the loan repayment ledger and issues a `VIRT-` reference/receipt; it does not debit an account or move money. Do not connect this simulator to production payment flows or treat its receipts as proof of funds. Use an authorized provider integration before accepting real payments.

Customers and employees with an existing loan application may repay their own approved loans using the **Pay Loan** action on their loan dashboard. Bank-account repayments debit an active account owned by the borrower at the loan's bank and sub-branch. The account debit, account transaction, loan allocation, receipt, and idempotent payment record are committed together in a MongoDB transaction. The database must support transactions (normally a replica set). A direct account payment moves the account balance inside this system; it is not an external bank transfer.

System Admins, Bank Admins, and Sub-branch Managers may also record a customer repayment they have already received, using the cash, mobile-money, or bank-transfer method. Bank Admins are limited to their bank and Sub-branch Managers to their assigned branch. Staff must confirm receipt; the system stores who recorded it and issues a receipt number. This staff-recording option does not debit a customer account or itself verify an external payment.

The signed-in employee's saved profile name identifies attendance records; employees do not re-enter their name each day. The system records check-in and check-out together under one Rwanda-local date. Check-out requires a separate consented selfie and is available from 5:00 PM Africa/Kigali time. Both photos are stored in Cloudinary as authenticated assets; photo asset IDs and consent times are kept in MongoDB. HR can view each photo through the bank-scoped endpoint, while photo data is not exposed in employee or report APIs. Exact JPEG file hashes are checked against other employee accounts to reject reused photo files; the system does not compare faces or visually similar photos. Before deploying this check to a database with existing attendance records, set `CLOUDINARY_URL` and any required `ATTENDANCE_ENCRYPTION_KEY`, then run `npm run attendance:backfill-photo-hashes` to register historical photos. Review and resolve any duplicate report before enabling the update. Attendance photo retention and deletion must follow the bank's approved policy.

Password recovery uses a one-time email code valid for 10 minutes and the configured SMTP service. For Gmail SMTP, use an app password and configure `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_SECURE=false`, `SMTP_USER`, `SMTP_PASS`, and optionally `SMTP_FROM` in the deployment secret manager. Guest mode previews the system with fictional data and no operational actions; feedback submission is the only write action available to a guest.

Loan applications, decisions, repayments, and defaults are stored in MongoDB and limited to the applicant, administrators, Bank Admins for their bank, or employees assigned to the loan's sub-branch.

The loan workflow has not been independently validated for compliance with current Rwanda lending regulations. Before production lending, the regulated institution's compliance team must verify and configure applicable BNR requirements, including disclosures, eligibility checks, pricing, affordability, and records retention. Do not treat this application as legally compliant without that review.

The System Admin can view and filter bank accounts and deposit history across every bank and sub-branch, inspect bank profiles and staff, and manage user roles and bank assignments. Employee accounts are assigned a bank and sub-branch. Each bank role has a scoped dashboard:

- Bank Admin: bank-wide member and employee administration, create and assign Sub-branch Managers and other staff, review loans across all sub-branches, and inspect the bank's customer accounts.
- Sub-branch Manager: register and manage members and review loan applications within the assigned sub-branch.
- General Manager / CEO: read-only branch overview and loan reports.
- HR Manager: bank-wide employee and customer-member directory.
- Finance Manager: bank-wide employee and customer-member directory (view-only) and payroll for verified staff in the assigned sub-branch.
- Accounts Manager: assigned sub-branch account ledger and account activation controls.

Bank Admins can view customer bank-account details across their bank; Sub-branch Managers and Accounts Managers are limited to their assigned sub-branch. Account activation controls remain limited to Accounts Managers. Customer dashboards provide account and balance information, transfers, deposits, loan applications and tracking, transaction history, and profile management. Role permissions are checked by the backend as well as hidden or shown in the frontend. Member directories and member status actions are scoped to the employee's bank or sub-branch; payroll and account controls retain their assigned sub-branch permissions. Only the System Admin can inspect data across all banks.

The notification bell records successful application activity (such as registrations, approvals, account changes, payroll batches, and loan actions) in the browser's activity history. Selecting "View all" opens the complete saved activity list; request errors remain in their normal error messages and are not added as notifications.

Bank reports summarize employee and member counts/status, account balances, deposit totals, loan status and financial performance, and queued payroll totals. Large bank, customer, account, deposit, loan, employee, and payroll lists are paginated in the dashboard.

## HR dashboard

HR Managers have a bank-wide, view-only workforce dashboard with staff counts by role and sub-branch, active/pending/deactivated account counts, searchable and filterable employee records, account status, and account creation date. It does not infer employment dates, salary, attendance, or contract status because the current employee records do not contain those fields. Bank Admins remain responsible for staff access and branch assignments.

## Guest demo and feedback

Visitors may continue as Guest to view a read-only dashboard containing clearly labeled fictional sample metrics and charts. It does not load live bank or customer data and offers no account or transaction actions. Guests may submit anonymous feedback (category, 1–5 rating, and message); the form does not collect a name or email, limits the message to 2,000 characters, and is rate-limited to five submissions per IP per 15 minutes. System Admins can view the latest feedback and mark submissions reviewed.

## Mobile-money deposits

Deposits use Paypack cash-in. Configure `PAYPACK_CLIENT_ID`, `PAYPACK_CLIENT_SECRET`, `PAYPACK_WEBHOOK_SECRET`, and `PAYPACK_ENVIRONMENT` on the backend. Register `https://<your-api-host>/api/payments/paypack/webhook` as an active Paypack webhook for the matching Development or Production mode. The webhook signing secret is available from the webhook configuration in Paypack. Keep these secrets only on the backend.

Deposits remain pending until a valid `transaction:processed` webhook with a matching reference, amount, phone number, `CASHIN` kind, and successful status is received. A duplicate callback cannot credit the account twice. Paypack's client application's cash-in permission must be enabled.
